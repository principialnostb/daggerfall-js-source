# DFO Test Build — установка, обновления и закрытый EMC

DFO Test Build — тестовый Windows-клиент. Игрок один раз выбирает место установки, а затем получает обновления через лаунчер. Разработчик отправляет коммит в ветку `13.11-build`. Проверку, упаковку и публикацию выполняет GitHub Actions. Закрытые игровые ресурсы EMC выдаёт разработчик вручную через временную ссылку. Для этого канала используются GitHub Releases и существующая система приглашений, без отдельного сервера доступа.

Название в мастере, на ярлыке и в окне лаунчера — **DFO Test Build**. Числа вида `13.11.11` обозначают версию. Ветка, теги, отдельные имена файлов и папки профиля сохраняют исторические идентификаторы для совместимости с выданными клиентами. Ниже описано состояние, проверенное на переходных выпусках до [13.11.11](https://github.com/principialnostb/daggerfall-js-source/releases/tag/dfo-1311-v13.11.11).

## Игроку

1. Откройте **Download setup** в описании выпуска тестового канала. Ссылка ведёт на графический мастер `DFO-Test-Build-Setup.exe`. Игровой патч может ссылаться на мастер из более раннего выпуска. Для перехода со старой сборки доступен [мастер с исправленным TLS](https://github.com/principialnostb/daggerfall-js-source/releases/download/dfo-1311-v13.11.11/DFO-Test-Build-Setup.exe).
2. Для первой установки выберите **New installation**, затем **Browse** и новую или пустую папку. Чтобы использовать уже скачанный клиент, выберите **Check and update an existing installation**. Можно указать саму папку клиента или родительскую папку, содержащую `client`.
3. Мастер скачивает внутренний установщик оболочки, сверяет SHA-256 и запускает установку в выбранное место. При переходе со старого `DFO Online Mod.exe` новая оболочка размещается в подпапке `DFO Test Build` внутри найденного клиента. Сохраните старую папку на время переноса. Лаунчер ищет прежние игровые файлы, проверяет размер и хеш, использует совпавшие и скачивает недостающие или изменившиеся.
4. В дальнейшем открывайте ярлык **DFO Test Build**. Лаунчер проверяет публичный выпуск, подготавливает игру и применяет изменение оболочки при перезапуске. Для закрытого контента тестер активирует приглашение и устанавливает EMC по предложению, полученному от разработчика. Лаунчер проверяет доступ до обновления, при фокусе окна и каждые 30 секунд. Когда проверка версии получает список публичных релизов GitHub, лаунчер обновляет ленту заметок из того же ответа. При обнаруженном отзыве или выходе кнопка запуска блокируется, а сетевые загрузки прерываются. GitHub Releases остаётся публичным. Лаунчер сначала проверяет и применяет обновление. При подготовке патча лаунчер показывает счётчик проверенных локальных файлов, затем объём скачивания. После обновления открывается установка EMC, и перед запуском проверяются приглашение и готовность пакетов. В **Test access → Remove EMC** можно удалить оба локальных пакета с подтверждением и затем повторить установку. При сетевом сбое кнопка **Retry update** повторяет проверку GitHub. Для старых копий с кнопкой **Download** нужен переход через графический мастер.

## Разработчику

| Изменение | Что делает выпуск | Что получает установленный клиент |
| --- | --- | --- |
| Игра, CSS, сценарии интерфейса или логотип внутри окна | Собирает публичную игру вместе с интерфейсом, формирует манифест и pack. Для обычного патча сохраняет ссылку на действующий мастер | Сравнивает локальные файлы с манифестом и скачивает нужные диапазоны pack. |
| Основной процесс Electron, preload, зависимости оболочки, мастер или иконка Windows | Выпускает оболочку NSIS, blockmap, метаданные `latest.yml` и графический мастер | Лаунчер через electron-updater получает совместимую оболочку и перезапускается. Размер скачивания зависит от доступности блочного обновления. |
| Компоненты EMC | Упаковщик готовит базовый пакет и отдельный пакет лиц для закрытого выпуска | Тестер получает временную ссылку вручную. При установке предложения проверяются размер и SHA-256 компонентов. Лаунчер показывает этап и скачанный объём каждого пакета. Через 30 секунд без ответа или новых данных он завершает попытку, чтобы можно было повторить загрузку. |

Обычный выпуск начинается с push в `13.11-build`. В Actions откройте **13.11 test client** для нужного SHA, проверьте завершение шага публикации и ссылку **Download setup** в опубликованном релизе. При правке мастера или оболочки сначала использовалась ветка `codex/1311-launcher-preview`: она сохраняет артефакт и выполняет сквозной тест установки на одноразовой Windows. Тест замены оболочки ожидает собранный NSIS. Чисто игровой патч можно проверить профильными тестами и сравнением манифестов. Точные условия запуска, упаковки и публикации приведены в [workflow](../../.github/workflows/release-13.11.yml) и [упаковщике](../../tools/prepareTestUpdate.mjs).

Публикация сначала создаёт черновик, загружает файлы, затем открывает релиз. В выпуске оболочки `DFO-Test-Build-Client.exe` служит внутренним пакетом. Копия мастера с историческим именем `DFO-13.11-Setup.exe` нужна существующим версиям для поиска обновления. Ссылку для игрока формирует workflow. [Сборка мастера и оболочки](../../tools/buildTestShell.mjs)

Список приглашений тестер читает из публичного файла ветки через raw.githubusercontent.com. Изменения могут появиться с задержкой кеша GitHub. Администратор записывает изменения через GitHub API. При временной ошибке проверки Play блокируется. Начатая передача может продолжаться до первой неуспешной проверки спустя 90 секунд с успешного ответа. Выход и обнаруженный отзыв сразу отменяют передачу. После входа работает и периодическая проверка релиза.

При обрыве EMC повторите установку. При истечении ссылки получите новое предложение. Для того же SHA-256 клиент запрашивает оставшиеся байты. Полный ответ сервера запускает загрузку компонента заново. Комплект переключается после проверки всех частей. При прерванном переключении клиент завершает его при следующем обращении. Remove EMC очищает также частичные загрузки. При выпуске оболочки Windows CI проверяет её установку и перезапуск до публикации.

### Памятка для следующего изменения

**1. Найдите рабочее дерево канала.** В этой установке это соседний каталог `13.11-build`. В другом клоне путь может отличаться. Перед правкой посмотрите `git worktree list`, затем в выбранном дереве выполните `git status -sb`, `git remote get-url origin` и `git fetch origin`. Публичный канал использует репозиторий `principialnostb/daggerfall-js-source`. Команда `git log --oneline origin/13.11-build..HEAD` показывает также старые локальные коммиты, которые попадут в push.

**2. Выберите исходник по месту изменения.**

| Задача | Что править | Как проверить результат |
| --- | --- | --- |
| Кнопка, текст, вёрстка или рисунок в окне лаунчера | [HTML](../../app/launcher/index.html), [CSS](../../app/launcher/launcher.css) и сценарии рядом с ними в `app/launcher/` | Открыть заново окно лаунчера после применения игрового патча. Новая операция с системой через Electron также потребует изменения оболочки. |
| Общий логотип лаунчера и меню игры | [Единый PNG](../../app/launcher/daggerfall-online.png). При смене пропорций обновить размеры в HTML и [brandMark.js](../../src/ui/brandMark.js), проверить центровку в меню и заставке | Сверить SHA-256 исходника с двумя записями опубликованного манифеста: `desktop-launcher/daggerfall-online.png` и `assets/daggerfall-online-<хеш>.png`. |
| Иконка ярлыка Windows | [Исходный ICO](../../app/test-build.ico). Его использует [сборщик оболочки](../../tools/buildTestShell.mjs) | После обновления и перезапуска проверить ярлык установленного клиента. Если видна старая иконка, сначала сверить версию и путь к EXE в свойствах ярлыка. |
| Системная логика лаунчера или установка | [Основной процесс](../../app/main.cjs), [preload лаунчера](../../app/launcherPreload.cjs), модули `app/lib/` или [мастер Windows](../../tools/testUpdateSetup.cs) | Прогнать проверку оболочки на preview, включая установку и повторное открытие окна. Для мастера проверить обе кнопки, путь с пробелами и HTTPS-загрузку. |
| Закрытые ресурсы | Следовать разделу «Как выдавать закрытый EMC» ниже | Проверить приватность целевого репозитория, состав пакета и выдачу временной ссылки. В публичную ветку коммитятся только предназначенные для неё исходники и ресурсы. |

**3. Проверьте и отправьте коммит.** Перед push примените проверки из [AGENTS.md](../../AGENTS.md). Для общего логотипа есть и короткая адресная проверка:

```powershell
node --test --test-name-pattern="Test build wordmark|Wide test build" test/ui/brand.test.js
```

Пример для замены только PNG с прежними размерами в синхронизированной ветке `13.11-build`:

```powershell
git add -- app/launcher/daggerfall-online.png
git diff --cached --stat
git diff --cached --check
git commit -m "Update the launcher and menu wordmark"
git push origin HEAD:refs/heads/13.11-build
git rev-parse HEAD
```

Если push отклонён как `fetch first`, выполните `git fetch origin`, посмотрите входящие коммиты и перенесите свои локальные коммиты поверх `origin/13.11-build` через `git rebase origin/13.11-build` при чистом рабочем дереве. После разрешения возможных конфликтов повторите проверки и обычный push. Так сохраняются изменения списка приглашений, которые могут поступить между началом работы и публикацией.

Для предварительной проверки оболочки отправьте подготовленный коммит в `codex/1311-launcher-preview`. После успешного Windows-прогона публикуйте проверенный SHA в `13.11-build`. Готовые EXE, ZIP, pack и манифесты создаёт workflow. Подготовка отдельного локального архива и ручное прикрепление EXE к обычному релизу не требуются.

**4. Дождитесь релиза и проверьте установленную копию.** Найдите прогон по SHA и ветке в [Actions](https://github.com/principialnostb/daggerfall-js-source/actions/workflows/release-13.11.yml). Для публичного выпуска проверьте успешный шаг **Publish the public client**, опубликованный тег и файлы релиза. Откройте уже установленный лаунчер и проверьте именно изменённый экран или ярлык. Два проверенных примера:

- [13.11.12 — логотип](https://github.com/principialnostb/daggerfall-js-source/releases/tag/dfo-1311-v13.11.12). Опубликованы игровой манифест и pack. Для перехода с 13.11.11 клиент по манифестам запрашивал около 15,3 МБ, включая изменившиеся файлы сборки.
- [13.11.13 — иконка](https://github.com/principialnostb/daggerfall-js-source/releases/tag/dfo-1311-v13.11.13). Дополнительно появились пакет оболочки, blockmap, `latest.yml` и мастер. Извлечённая из опубликованного EXE иконка совпала с исходной.

Push в релизную ветку запускает сборку и при правке одной документации. Сейчас workflow исключает только изменение одного файла списка приглашений. Если новый выпуск не нужен, документацию можно сохранить отдельным локальным коммитом и отправить со следующим плановым обновлением.

## Как выдавать закрытый EMC

Исходные разрешённые ресурсы берутся из каталога с подпапкой `Mods`. Создайте пустую выходную папку и выполните две команды для нужных компонентов. Упаковщик выводит имя, размер, число файлов и SHA-256 результата. [Упаковщик EMC](../../tools/prepareEmcOffer.mjs)

```powershell
node tools/prepareEmcOffer.mjs "<каталог с Mods>" "<выходная папка>"
node tools/prepareEmcOffer.mjs "<каталог с Mods>" "<выходная папка>" --faces-only
```

Пакеты публикуются в закрытом репозитории `principialnostb/dfo-13-11-test-releases` под тегом вида `emc-1311-vN`. Разработчик копирует временный код `DFO1-…`, тестер вставляет его в **Install EMC**. Код содержит сжатое предложение GitHub и проверочные суммы. Лаунчер принимает и старый JSON. Обе кнопки открывают одну форму, а EMC использует общую полосу прогресса. При истечении ссылки сформируйте новое. Изменение обычной игры не требует повторной выдачи EMC. Автоматическая сборка EMC по push в закрытую ветку остаётся отдельной задачей. [Выдача приглашений и ссылок](../../app/lib/publicTestChannel.cjs) · [Проверка и установка пакетов](../../app/lib/emcReleasePack.cjs)

Приглашение разрешает доступ в штатном клиенте. Для получения закрытых файлов также нужна действующая ссылка. Уже выданную ссылку можно передать до её истечения. Отзыв приглашения действует при следующей проверке доступа и не удаляет полученные файлы с компьютера тестера.

## Ошибки и проверенные исправления

| Симптом | Причина и действие |
| --- | --- |
| Мастер сразу устанавливает программу, пропал выбор папки, на ярлыке появилось «13.11» | В 13.11.9 внутренний однокнопочный NSIS стал пользовательской точкой входа. В 13.11.10 восстановили графический мастер с двумя режимами и названием DFO Test Build. Используйте **Download setup**. |
| Папка с пробелами принимается формой, но клиент оказывается вне выбранного места или установка завершается ошибкой | При восстановлении мастера обнаружилась ошибка передачи пути внутреннему установщику. Теперь мастер передаёт выбранный путь отдельным значением окружения. Проверка на Windows включает установку в такую папку и сохранность старого файла. |
| На этапе **Preparing the launcher…** появляется «Не удалось создать защищенный канал SSL/TLS» | В мастере 13.11.10 публичная загрузка начиналась до включения TLS 1.2. Закройте старый мастер через **Отмена** и запустите версию 13.11.11 или новее. В исправленном EXE TLS 1.2 включается до первого сетевого запроса. |
| Install EMC сразу сообщает об ошибке | При каждом нажатии лаунчер проверяет приглашение через GitHub до запроса пакета. При отказе API окно показывает HTTP-код. Ошибки формата предложения, записи на диск и контрольной суммы имеют отдельные сообщения. Для диагностики передайте текст ошибки и версию лаунчера. Ссылку передавать не требуется. |
| Обновлённый EMC имеет ту же длину, но тестер видит старые ресурсы | Раньше клиент мог пропустить уже читаемый компонент. При обработке временного предложения теперь сверяется SHA-256. Повторите установку с актуальным предложением. |

Локальная проверка TLS воспроизвела исходную ошибку, затем тем же путём скачала все 138 212 832 байта клиента 13.11.10 и подтвердила SHA-256. Проверка в Actions выполняет HTTPS-запрос из собранного мастера с исходными устаревшими настройками процесса. Тест замены устанавливает предыдущую тестовую оболочку, дожидается скачивания, установки и открытия окна новой версии. [Проверка TLS](../../tools/verifyTestSetupTls.ps1) · [Проверка установки и перезапуска](../../tools/verifyTestShellSwap.mjs) · [Выпуск исправления](https://github.com/principialnostb/daggerfall-js-source/actions/runs/44355883751)

## Скорость и оставшаяся работа

Измеряйте отдельно время от push до публикации, объём выгрузки CI, объём скачивания игроком и время применения на диске. В контрольном прогоне 13.11.9 выпуск занял 9 мин 26 с. На локальной контрольной сборке упаковка заняла 123 с с пустым кешем и 20 с с прогретым. В изолированном профиле после установки 32 881 файла проверочный патч одного CSS-файла передал 22 байта. Это результаты конкретных прогонов. [Рабочий выпуск 13.11.9](https://github.com/principialnostb/daggerfall-js-source/actions/runs/44341766894)

Кеш Brotli экономит время повторного сжатия. CI пока выгружает полный игровой pack, а клиент при подготовке новой версии может копировать на диске уже имеющиеся файлы. Следующие цели — сократить повторную выгрузку неизменившихся данных и стоимость локального копирования, сохранив проверку хешей, работу после пропуска нескольких релизов и восстановление после прерванного обновления.

Для диагностики розовых материалов EXE пишет в Diagnostics/integration.ndjson событие character-material-resolution с именем текстуры, слотом и известным путём модели. При отсутствии базовой текстуры у замены тела или одежды клиент пробует тот же путь модели в следующем архиве. У брюк и обуви с единственной формой на обе ноги треугольники распределяются по весам левой и правой ног скелета. Это сохраняет независимую замену каждой стороны экипировкой.
